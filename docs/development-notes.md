## 1. 项目是什么

一台海尔 topsir H9（9.7" 墨水屏、Android 4.0.4）变成电脑的外接屏，显示两样东西：

- **信息看板**：天气 + 全球新闻 + 中文热搜 + 日期时间，每分钟更新
- **歌词面板**：网易云音乐 PC 客户端的当前曲目 + 滚动歌词 + 播放控制

架构是**PC 渲染 → 局域网 HTTP → 设备拉图**。设备端不做任何计算，只负责"取图、贴图、上屏"。

这个分工不是随便定的，是被三件事逼出来的：

| 约束 | 后果 |
|---|---|
| Android 4.0.4 的 TLS 只到 1.0 | 设备**上不了现代 HTTPS 网站**，联网取数只能在 PC 做 |
| i.MX6SL 单核 1GHz + 默认堆 16~24 MB | 设备端只能解码位图，**不能跑渲染/解析逻辑** |
| 墨水屏每次刷屏要 300~600ms 且会闪 | 必须**只在内容真变时才刷**，且尽量只刷变化的那块 |

## 2. 架构铁律（改代码前必读）

### 2.1 看哪个面板 = 服务端说了算

状态在 `server.py::PanelState`。设备每 4 秒 `GET /panel` 跟随；GUI、`POST /panel`、
设备长按菜单的 `panel_toggle` 改的是**同一份状态**。

> **`dashboard.conf` 里的 `mode` 只是"连不上服务端时的开机兜底"，不是现场开关。**
>
> 这条是被 bug 逼出来的：早期把模式写在设备配置里，结果用户想切换只能插 USB 改文件再重启 App
> ——而人明明就坐在电脑前。**把一个高频操作做成必须碰设备，是交互设计的错，不是实现 bug。**

### 2.2 设备端只有一个轮询循环

`tick()` → `GET /panel` → `fetchDash()` 或 `fetchMusic()`。

以前 dash / music 是两套并行状态机，那正是"两边状态打架"的来源。
换面板时要 `heldFid = -1` / `dashRev = 0` / 回收 `fullBmp` / `clearZones()`。

> `fullBmp` **必须回收**。一张 825×1200 ARGB_8888 = **3.78 MB**，换几次面板就 OOM。

### 2.3 端口必须独占，子进程必须随 GUI 一起死

**Windows 的 TCP 监听默认带 `SO_REUSEADDR`** → 第二个进程绑同一端口**也不报错**（Linux 会失败）
→ 内核**随机分派**连接 → 约一半请求"连上但零字节"。而**每个进程单独看都是健康的**。

这个 bug 极阴：它表现为"有时准有时晚一句"，谁都不会想到是端口。

修法两层：
1. 绑定前用**不带 `SO_REUSEADDR` 的裸 socket** 试绑，被占就 `SystemExit(2)`
   —— **不能用 connect 探活**，那探不出来
2. GUI 起服务后 `_adopt_into_job()`（Job Object + `KILL_ON_JOB_CLOSE=0x2000`）+ `atexit` 兜底

> **`RemoteDisconnected` ≠ "连不上"**。TCP 是连上了的，只是对端一个字节都没回就关了
> ——这是"服务坏了"，不是网络故障。文案不能混，混了就会把人引去查网络。

### 2.4 渲染路径绝不联网

取数归后台守护线程（看板是 `server.Refresher`），渲染只读磁盘缓存。
理由：渲染在 HTTP 请求线程里跑，一旦网络卡住，设备端所有轮询都会超时。

### 2.5 指纹里必须含"所有会让画面变的东西"

看板的指纹 = `config.json` 的 size:mtime + 三个数据缓存的 size:mtime + **分钟桶**。
少算任何一项，表现都是"屏上的东西不更新" —— 而且是**静默的**，没有任何报错。

## 3. 墨水屏逼出来的设计

### 3.1 只贴脏块，不重拉整图

服务端把画面切块，逐块和上一帧比像素，只回变化的那几个矩形的 base64 PNG。

- 实测 **1.6 KB vs 整帧 67 KB（省 97.5%）**
- 校验时比 **`res.image`**，不是 `rr._prev` —— `_prev` 是量化前的 L 原图，比了会误报

### 3.2 帧号（frame_id）协议：序号必须在增量完整生效后才推进

```
N == 当前帧   → 回 up_to_date
N == 当前帧-1 → 回变了的那几个矩形
其它         → 回整帧
```

**⚠️ 这里有个会让故障永不自愈的顺序陷阱**（踩过，代价是三轮排查）：

```java
// 错：帧号在贴图循环之前采纳
if (fid >= 0) heldFid = fid;
for (...) { /* 贴脏块，这里抛了 */ }
```

循环中途一抛 → **帧号已前进，但脏块一块都没贴上** → 下一轮贴到"本来就错"的底图上
→ **贴一万次还是错的**，没有任何出口 → 永久定格。

**规矩：帧号只在"干净的一轮"之后才采纳**（`up_to_date` / 整帧解码成功 / `badTiles == 0` 走到底）。
出岔子立刻 `heldFid = -1`。全文件恰好 3 处采纳，测试里有计数断言钉着。

> 推广：**凡是"客户端凭序号请求增量"的协议，序号必须在增量完整生效后才推进。**

### 3.3 触摸分区随画面下发

服务端画按钮时把矩形一起给设备，设备只做 FIT_CENTER 坐标命中。
**改版式不用重编译 APK**（实测 10/10 命中，留白区不误触）。
切到看板时必须 `clearZones()`，否则会拿歌词面板的分区误判点击。

### 3.4 同步靠"对齐取图时刻"，不靠"提前唤醒"

这是整个项目最重要的一条认知，值得单独讲：

> **设备取到的那一帧，反映的是「取图那一刻」的曲内位置。**
> 歌词 100.9s 出现，你在 100.3s 醒来取图 → 拿到的还是旧句子，屏上什么都没变。
> **所以「让设备早醒」根本不能让屏上的字提前。**

正解：把「歌词行」本身也当作一个唤醒点，和整秒边界取 `min`，谁先到醒谁。
实测最坏延迟 **1500ms → 600ms**。剩下的 600ms 是 HTTP + 解码 + 墨水屏波形的固有代价，
**物理消不掉**（除非让歌也晚 0.6s 播）。

**"提前量"这个思路踩了三次，三种踩法都不同：**

| 踩法 | 后果 |
|---|---|
| 对"整秒边界"减提前量 | 整秒剩余永远 ≤1000ms → **每秒醒两次，刷新率永久翻倍**。"早醒不能让时间走快"是本质原因 |
| 把「歌词−LEAD」当每轮重算的目标 | 它是固定值，提前醒来后再算还是它、而现在已经越过它 → 永远返回 50ms → **50ms 空转** |
| 对齐目标落在歌词"之前" | 那一帧不含新句子，等于没做（实测 0 改善） |

### 3.5 进度条必须量化到整秒

进度条横跨 825px 全宽，用毫秒级 `position_ms` 去画 → **每秒重画 30~60 次**，
即使歌词一句没换，设备也一直收脏块、屏一直闪。实测 **12 秒刷 40 次、累计脏面积 464% 整屏**。

修法：渲染前 `qpos = pos // 1000 * 1000`。→ **40 次降到 12 次**。

### 3.6 任何"下限/节流"钳位，在做精确调度时都是敌人

三处曾经把 50~70ms 的对齐信号抬到几百毫秒：

- GUI 的 `max(0.6, wait)` → 改成 `max(0.05, ...)`
- `service.py` 的 `MIN_FRAME_INTERVAL = 0.6` → 会**正好挡住对齐那一刻的帧**，拿回旧句子，
  表现为"有时准有时晚一句"（最难查的一种）
- Java 的 `clampDelay` 400ms 下限 → 改成 40ms

> **加钳位之前先问：它会不会吃掉小值？**

### 3.7 看板：分钟对齐 + 3 秒提前量

**曾经的真 bug：看板时钟是卡死的。** 指纹只算 `config.json` 的 mtime+size、不含时间
→ "指纹没变 → 回缓存不重画"恒成立 → 屏上时间永远停在第一次渲染那刻。
用户以为"没设成 70 秒刷一次"，实际是**永远不刷**。

不要用固定 70 秒：**会跳分钟**。10:34:50 刷出 `10:34`，下次 10:36:00 刷出 `10:36`，
那么 `10:35` 这一分钟**从头到尾没显示过**，且时钟最多滞后一个周期。

现在的实现：
- **分钟桶**（指纹含 `epoch // 60`）：每分钟恰好闪一次、不跳分钟
- **3 秒提前量（`render.RENDER_LEAD_S`）**：渲染用 `now + 3s` 当基准，
  且**指纹和画面必须共用同一个时刻** —— 否则请求卡在 `:59.x` 会渲染旧分钟，
  上屏 4 秒后又闪一次（约每 15 分钟多闪一次）

> 与歌词的 `lyric_lead_ms` 完全同构：**为"画面被看到的时刻"渲染**，而不是为"现在"。
>
> ⚠️ 提前量的副作用：**"还属于本分钟"的窗口是 `:00`~`:56`**，`:57` 起就算下一分钟。
> 写测试断言时别再按 `:58` 写（我自己就写错过）。

## 4. 设备端（Android 4.0.4）

### 4.1 `BitmapFactory` 解出的位图一律当 immutable

**这是"解析失败"三轮悬案的真凶**，值得单独记：

```
IllegalStateException: Immutable bitmap passed to Canvas constructor
```

`BitmapFactory.decodeByteArray()` 默认返回 **immutable** 位图，而 `Canvas` 的构造器
**硬性要求 mutable**。贴脏块的 `new Canvas(fullBmp)` **必然抛，100% 复现**，
跟网络、跟数据、跟服务端**毫无关系**。

**为什么表现为"偶尔成功一次"**：抛了 → `heldFid = -1` → 下一轮走整帧；
整帧路径把 immutable 位图交给 `ImageView` **照样能显示** → 那一轮屏上看起来刷出了新内容，
人以为"成功了"。下一轮再要脏块，又撞同一堵墙。
→ 这就是"大部分时间在重试 + 十几秒才动一下"的完整解释。

**修法**：统一出口 `asWritable(bmp, needWritable)`
`isMutable()` 短路 → `copy(cfg, true)` → 复制失败（OOM）**退回原图而不是丢掉**。

两个赋值点都要过它（整帧那条路**不走** `swapInDashFrame`，自己内联赋值）。
**这次拷贝最容易被人当冗余删掉，删了就 100% 复现** → 已写成结构性断言。

> **一般教训**："服务端怎么验都是好的、设备却一直报错" → 去看两者的**差异面**（平台/运行时），
> 不要继续加深对服务端的验证。这个案子在服务端侧的验证投入已严重过量
> （JSON 合法性、字段类型、字符级扫描、PIL 复刻整个 `handleCrops`…全绿），
> 而真凶是一句 `new Canvas(immutable)`。

### 4.2 UI 线程的 Runnable 是"闪退"的**唯一**入口

任何漏出去的 `Throwable`（含 `OutOfMemoryError`）= App **立刻闪退**，没有救场机会。

必兜的三类：`decodeByteArray` / `createBitmap(rotate)`（OOM）、
`recycle()`（已回收的位图上会抛）、`Base64.decode`（损坏字符串上**会抛**，不是返回 null）。

规矩：
1. 每个可能抛的调用各自 try
2. Runnable 体**外层再套一层** `catch (Throwable)`
3. `setStatus` 自己也 try —— 它专门用来报错，不能自己变成崩溃点

**11 个 Runnable 全部兜底**，其中**最致命的两个都不是"干重活"的那个**：

- **`tick()` 本身**（整条轮询循环的入口）。它被 handler 直接调起，异常**没有任何中间层能接住**
  → 心跳断掉，屏上停最后一帧，**连错误都不打**
- **面板轮询那个 Runnable**（主心跳），一抛 `tickRunnable` 就再也不会被排上

> ⚠️ **兜底时必须把下一跳排上**（`sleepThenTick`）。只吞不排 = 把循环杀了，
> 比不吞还糟 —— 用户只会觉得"今天怎么不刷新"，比崩溃更难查。
> 兜底时还要**复位防重入标志**（`polling = false; fetching = false;`），
> 否则下一轮 `tick()` 一进来就 `return` —— 看着还在转，实际永远不干活。

> **"继续跑"比"不崩"优先级更高。**

### 4.3 最贵的报错是"解析失败"这种没有下文的

同一句至少对应三种修法完全不同的病：`JSONException`（结构坏）、
`NumberFormatException`/`ClassCastException`（类型不对）、`Base64` 解码错（数据坏）。

改法：状态行带**异常短名 + message 头一段 + 第几步**。
更进一步：**解析失败时把原始 body 落盘**（`h9dash_bad.txt`，只留最近 3 条）
—— 这是终结这个悬案的关键一步，没有它永远在猜。

### 4.4 部署了新 APK ≠ 新代码在跑

只看两样：

1. 设备盘 `h9dash_screen.txt` 的 **mtime**（App 启动时写）是否**晚于** APK 部署时间
2. **新版才有的诊断文件在不在**（如 `h9dash_bad.txt`）

踩过：APK 23:50 部署，`h9dash_screen.txt` 还是 23:55（旧进程），`h9dash_bad.txt` 不存在
→ "修好了没"**永远得不到结论**。

> **所以跟用户说"请重装"时，一定要说清"装完必须完全退出 App 再打开"。**

### 4.5 APK 字节数不是有效判据

改了代码 APK 字节数仍可能一模一样（实测两次 37267 bytes）。
**只能靠内容验证**：

1. 解开 APK 取 `classes.dex`，与 `build/classes.dex` 比 SHA256
2. 在 dex 常量池里找**这次新加的方法名 / 文案**（如 `asWritable`）

> 注意：**只出现在注释里的文字不会进 dex**。用它当探针会得到假的"没编译进去"。

## 5. 服务端与协议

### 5.1 token 走查询参数 `?t=`，不是请求头

免 token 的只有两个：
- `/health` —— 设备靠它拿 token，所以必须免鉴权
- `/panel` —— 设备得在鉴权**之前**就知道该拉哪个端点

### 5.2 `/health` 里没有 `token` 字段

它只把 token **拼进 `dash_url` / `music_url`**。要拿 token 得 `split("t=", 1)[1]`
—— 读 `h["token"]` 永远为空，会得出"token 不一致"的**假警报**。

### 5.3 判"8765 上跑的是哪份代码"

看 `/health` 的 `service` + `server_version`（如 `H9Dash` + `H9Dash/1.2 Python/3.12.10`），
别只看端口通不通。

### 5.4 403 与连接失败必须分开报

403 = token 不匹配，**服务活得好好的**。混在一起报"服务没跑"，用户会去查网络/进程，白费功夫。

> GUI 的 `get_token()` 有"文件丢了就新生成"的自愈 → 会与服务端分叉 → 403。
> 这个自愈本身是好的，但必须让用户知道后果。

### 5.5 写服务端 harness 时必须自己补 `Handler.cache` / `Handler.token`

它们是 `main()` 里赋的类属性，不补全是 `None` → 所有 `/dash.png` 回 500。
表现为"缓存坏了"，其实是没初始化。

## 6. 网易云音乐那四条链路

### 6.1 当前曲目：窗口标题 + `webdb.dat` 反查

窗口标题（`歌名 - 歌手`）为主，用 `Library\webdb.dat`（SQLite，只读打开）反查 id/时长。

> `historyTracks` **会停更**（实测窗口标题已换 3 首、它落后 12 分钟）—— AI 漫游/电台场景它不写。
> 标题反查不到 id 的歌，再用**线上按名检索**补 id，但**宁缺勿错**（归一化精确匹配 ≥6 分才认）。

### 6.2 播放/暂停：只有 WASAPI 峰值电平可靠

音频会话的 `state` 在暂停时**仍是 `1 (Active)`**，靠它永远显示"播放中"。
用 `IAudioMeterInformation` 峰值 > 0.0008 算出声，迟滞：连续 2 次静音才判暂停。

> ⚠️ **未解**：`device_peak()` 实测恒为 `2^-32`（10 次采样完全相同），阈值却是 `0.0008`。
> 它读的是**默认渲染端点**的 meter，不是 per-session meter —— 端点不对就恒返回极小常量。
> **"歌在放但被判 paused"时优先查这里。**

### 6.3 进度：自建时钟

对齐点按可靠性排序：切歌 > `playingCount` 停下事件 > 循环回绕。

`playingCount` 每次停下写一行（`updateTime - playDuration` = 本轮真实起播时刻，毫秒级）。
单曲循环时 `historyTracks` 不新增但**它**会新增 → 循环也能发现。

### 6.4 控制：媒体键注入

`VK_MEDIA_PLAY_PAUSE` (0xB3) / `Ctrl+Alt+←→` / `Ctrl+Alt+↑↓` / `Ctrl+Alt+L`。

> **`Ctrl+Alt+P` 不是播放暂停**（被客户端注册到别处去了）。只有 `VK_MEDIA_PLAY_PAUSE` 稳定可用。
> 这是调研时写错、实测推翻的结论。

### 6.5 调研阶段被推翻的结论（别再试）

| 调研时以为 | 实测结论 |
|---|---|
| `Ctrl+Alt+P` = 播放/暂停 | ❌ 无效，只有媒体键可用 |
| 读 `webdata\lyric\` 本地歌词缓存 | ❌ 3.1.40 上该目录**不存在**，歌词只能走接口 |
| `orpheus://playlist/{id}` 能切歌单 | ❌ 协议确实注册了，但那是 CEF 内部 scheme，不是深链接。两次 25s 对照实验零影响 |
| SMTC 读进度 | ❌ 客户端**根本不发布媒体会话**，`winrt_utils.dll` 都没加载 |
| 读桌面歌词窗口文本 | ❌ 那个窗口是**自绘**的（Class=DesktopLyrics，无任何子控件） |

### 6.6 歌词提前量：分清动的是哪一层

两次都要求"歌词对早"，做法却**相反**：

| | 动什么 | 适合 | 代价 |
|---|---|---|---|
| `lyric_earlier`（nudge） | **整体移动 `position_ms`** | 时钟本身偏了 | 进度条、剩余时间一起偏 |
| `lyric_lead_ms`（新） | **只移动"选句基准"** | 显示比歌慢半拍 | 无（逐像素验证过进度条不变） |

用户说"歌词有延迟"要的是**后者**。

> ⚠️ **唤醒点必须用同一基准扣掉 lead**，否则"画面提前变了、设备按原时刻才醒" = 白跑一趟，反而更晚。
> 越界时给 `pos + 1`（立刻醒），**绝不能给 `None`** —— `None` 被 `next_change_ms`
> 当成"没有歌词行"而只靠整秒唤醒，反而更慢。

## 8. Windows / Python 环境坑

### 8.1 ⚠️ 中文 Windows 上 `print` 会致命

控制台是 936(GBK)，Python 选 stdout 编码看的是**代码页 / `PYTHONIOENCODING`**，
**跟源码里那句 `# -*- coding: utf-8 -*-` 毫无关系**。

`◀ ▶ ⇄ ✓ ✗ ─` 这些符号 GBK 编不出来 → `UnicodeEncodeError` 直接在 `main()` 里把进程打挂。
（这个 bug 的真实后果：服务根本没起来，而设备端报"获取失败"，所有人都在查网络。）

**规矩**：任何要打中文的入口，**第一件事**就是 `render.fix_console_encoding()`
（共享实现，必须在**任何 print 之前**），且**装饰性符号能不写就不写**。

> 只打中文则成乱码（`H9 �����` 就是"没对齐编码"的指纹）。

### 8.2 `.ps1` 必须 UTF-8 **带 BOM**；`.bat` 必须纯 ASCII

PowerShell 5.1 **没有 BOM 就按 ANSI(936/GBK) 解码**。用 UTF-8 无 BOM 保存中文注释，
字节被误读后**可能吞掉换行** → 注释和下一行代码粘成一行 →
报 `表达式或语句中包含意外的标记"}"`，**指到完全无关的行**。

> **这个坑连踩三次**（两个待改的 `.ps1` + 自己写的三个诊断脚本）。

诊断法（值得复用）：
1. `git show HEAD:<file>` 取原版对比头三字节：`EF BB BF`（有 BOM）vs `5B 43 6D`（无）
2. 同一段文本**分别按 UTF-8 和 GBK 各跑一次 `[Parser]::ParseFile()`**
   —— 哪个 0 错误就知道文件真实编码
3. 修法：`New-Object Text.UTF8Encoding($true)` 重写成 **UTF-8 带 BOM + CRLF**

`.bat` 是 cmd.exe 按代码页解析，UTF-8 中文会把整行读烂。
启动脚本还有一条规矩：**校验谁就启动谁**（同一个解释器 `import tkinter, PIL` 预检）。

### 8.3 `(x or {})` 只挡 None/空值，挡不住"非空非 dict"

```python
songs = ((data.get("result") or {}).get("songs")) or []   # ← 元凶
```

网易云在**限流/风控**时会把 `result` 变成字符串（也见过 list）→ `AttributeError`。

**为什么不能当 warning**：`search_songs` 是"窗口标题反查 id"的兜底，它一挂，
AI 漫游/电台/云盘里不在本地曲库的歌就**永远认不出 id**，表现为"歌词未找到"；
而控制台只留一行像 warning 的东西。**这是静默失效。**

> **规矩：凡是调用方会直接对返回值 `.get()` / `["k"]` 的函数，出口必须再过滤类型。**
> 否则漏出去的 `str` 会在几百行之外炸，报错离现场太远。
>
> 配套：读缓存时也判类型，把"脏缓存"退化成"缓存未命中"，**自愈**。

### 8.4 工具环境的坑（会反复遇到）

- **PowerShell 工具的 stdout 不回显** —— 结果统一 `Out-File` 到文件再读
- **Bash 工具能力不全**（无 `grep`/`ls`/`tail`/`cat`/`wc`/`sed`/`head`）→ 用 PowerShell 或 Python
- **Bash 的网络走代理** —— 访问自己的局域网 IP 会得 **502**。测本机服务要用 Python urllib 或同进程调用
- **后台进程会在工具调用结束时被回收** —— 要验常驻服务，必须**在同一进程内**起再测
- **`Add-Type` 被沙箱拦**，而且**一条命令里被拦 = 整条都不执行**
  → 读 zip 用 Python `zipfile`，别把编译和校验写在同一条命令里
- **安全删除钩子**：可能报 `SAFE_DELETE_FAIL_CLOSED` 但**实际已删**，用 `Test-Path` 复核；
  **批量删 ≥50 个文件会触发确认** → 分小批
- **嵌套双引号 SyntaxError**（踩过 6 次）：写中文注释时在 `"` 里再写 `"` 会挂，一律用 `「」`
- **`b"中文"` 直接 SyntaxError**（bytes 只能 ASCII）→ 用 `"...".encode("utf-8")`
- 跑测试务必加 `NO_PROXY=127.0.0.1,localhost` 并清掉 `HTTP_PROXY`
  —— 否则沙箱代理会把"连接失败"变成 **502**，那一档根本测不到

## 9. 测试怎么写

### 9.1 不能靠行为测试覆盖的缺陷，用**源码结构性断言**

OOM、时序刚好、要真机……这类缺陷往往**在源码里长得很特征**，那就直接当 lint 扫。

`_crash_test.py` 的例子：
- 每个 Runnable 必须有 `catch (Throwable)`
- 每个 catch 后面必须有 `sleepThenTick`
- `decodeByteArray` / `createBitmap` / `recycle` 之前必有 `try`
- 全文件 `heldFid = fid` **恰好 3 处**（计数断言）
- **底图赋值前 160 字符内必须出现过 `asWritable(`**

> ⚠️ **断言的范围要精确到"真正危险的那条路径"**（踩过三次）：
> 断言"贴图循环之前不许有 `heldFid = fid`"，会把 `up_to_date` / `full`
> 两个分支里**正确**的采纳判成错 —— 那两处安全（前者立刻 return，后者已把会抛的事做完）。
> **断言写粗了 = 白跑一轮去"修"没坏的代码。**
> 先问清"坏的机制是什么"，再把断言卡在那个机制上；配套加一条计数断言兜底。

### 9.2 测 GUI 要**真建一次控件树**

只查源码里有没有那几个标识符，发现不了"控件名拼错 / var 没建 / 布局抛异常"。
做法：`App.__new__(App)` + `tk.Tk()` + `withdraw()` + `threading.Event()`，不进 mainloop。

> 没有 mainloop 时 `root.after(0, cb)` 会在主线程之外碰 tkinter → `RuntimeError`。
> 但**不能**改成同步执行：那些回调**会再调 `root.after` 把自己排下一轮** → 无限递归。
> 正解：`after` 只入队不执行，测试侧 `wait_for(pred)` 边抽边等。
>
> 还有：`after` 的毫秒参数被忽略后，跨用例的回调会乱序 → **单跑绿、连跑红**。
> 正解不是"清空队列"，而是**等到本轮结果出现**（predicate 只认自己的值）。

### 9.3 `_*.py` 是长期资产，不是一次性探针

它们**未提交**（`_*` 被 gitignore），**删了没有第二份**。踩过一次，重建了一整轮。

> 清理临时文件时别一把梭全删。删之前先看一眼名字。

## 10. 诊断手册：现象 → 排查顺序

### 屏幕"定格"了

**先查服务端 `playing`，别先怀疑设备端解析。** 因果链：

```
playing=False → 进度时钟冻结 → next_change_ms() 只剩「暂停」(固定 2000ms)
              → lyric_next_ms=null → 画面永不改变 → 服务端回 up_to_date
              → 设备什么都不做
```

**设备端此时逻辑完全正确**，它在如实反映服务端的判断。

排查顺序：
1. `/music/status` 看 `playing` / `pos_ms`
2. `/music/crops` 看 `next_change_ms` 是否恒 2000、`lyric_next_ms` 是否 null
3. 判"真暂停还是误判"看三个旁证是否自洽：
   ① 窗口标题有歌名 ② `current_track().source` 是不是 `title+webdb`
   ③ `historyTracks` 的 `playtime` 与 `pos_ms` 吻合

### 设备报"获取失败 / 检查 PC 服务和 WiFi"

按这个顺序，**十次里八次是第一条**：

1. **电脑 IP 变了** —— 拿本机 IP 跟设备 conf 对比（最常见）
2. 服务没跑 —— `curl 127.0.0.1:8765/health`
3. **token 不匹配**（403 会伪装成网络故障）
4. 防火墙 —— `netsh advfirewall firewall show rule`

### 服务占着端口却不应答

`RemoteDisconnected` = **有两个进程绑了同一个端口**（见 2.3）。
找孤儿进程杀掉，或换端口。
